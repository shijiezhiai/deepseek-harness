# Agent Note: 用会话自己产生的观测来给危险带定尺

Status: implemented

[English](2026-10-28-context-pressure-nudge.md) | 中文

## 问题

每步读数告诉模型上下文有多大，但数字不是警报：一个读到 `~95k/100k` 的模型仍然得靠自己判断“这一步再加一次大范围 grep 就完了”。压缩随后以删除历史中段的方式解决压力，而这恰好是读数本该避免的昂贵结局。“模型知道数字”与“模型及时改变策略”之间只差一步，而仅靠读数填不上这一步。

## 决定

`@deepseek-ai/dsh-context-pressure-reminder` 在 `agent/pre-step` 接缝上增加第二条消息。当剩余余量窄于“再来一次大观测”时，guard 给模型即将执行的那一步追加一条警告：

```
[context: ~95.0k/100.0k tokens · 95% — one more large tool result can overshoot the window; prefer finishing a unit of work and writing findings to a file]
```

带宽取 `clamp(observationMultiplier × 最近最大的工具结果, minBandRatio × 窗口, maxBandRatio × 窗口)`，用会话实际产生过的工具结果来定尺，而不是一个固定比例。只读单文件的会话带宽窄、提醒得晚；一次调用就返回整个文件的会话带宽宽、提醒得早。这个不对称正是重点：风险的大小取决于**下一次**观测，而不是当前上下文的占用。

这个接缝有四个关键性质：

- **`agent/pre-step` 在步之前，而不是在工具之后。** post-execute 的读数描述的是已经花掉工具预算的那一步；警告必须到达模型仍能选择更便宜工具的时刻。这也是它不能作为第二条 post-execute 消息的原因：那时它想影响的决定已经不存在了。
- **先 await 下游，再追加。** 监听器调用 `await next()`，把消息追加到返回的决定之后。前插会让它排在其它监听器的上下文之前，更重要的是会排在压缩自己的 pre-step 改写之前；追加则保持每个监听器看到的步骤与其注册顺序一致。
- **`reject` 原样透传。** 被其它监听器否决的步骤不能因为一个 guard 而多出消息，信号已中止时也不发布任何东西。
- **警告绝不提压缩。** 在压缩入口点存在之前，模型没有可以调用的压缩工具，建议压缩等于描述模型并不具备的能力。它只说模型自己拥有的策略：收尾一个工作单元、把发现写进文件。

离开带宽即重新武装：guard 记住它警告时的占用，只要会话仍停留在带内就保持沉默，因此贴着上限的长会话只会读到一次警告，而不是每步一次。`minDeltaRatio` 本来就是读数的去抖参数，它同时决定会话停在带内继续增长时的重复频率。

所有未被实测的数字都放进配置——`observationMultiplier`、`observationWindow`、`minBandRatio`、`maxBandRatio`——因为合适取值取决于工作类型。默认值（`2`、`3`、`0.1`、`0.5`）是合理起点而非结论：目前没有任何录制会话针对它们做过标定。

## 考虑过的替代方案

- **固定的比例阶梯（25% / 50% / 75%）。** 否决：窗口的百分比说明不了下一次调用会花多少。一个只跑 `ls` 的 50% 会话毫无危险，对它报警只会训练模型忽略警告。
- **读取压缩的 `thresholdRatio` 并在其之上报警。** 否决：那会让 guard 的消息变成压缩策略的复述，而且压缩默认值一改，守着边界的数字就跟着漂移。压缩引擎本来也不公开只读阈值，这么做就得为复制一个 guard 不该拥有的决定而扩宽它的 Service Definition。
- **对超大工具调用硬拦截。** 否决：拒绝调用的 guard 等于劫持循环，而模型还没有机会规划一个更小的请求。
- **改写读数而不是新增消息。** 否决：读数是关于占用的事实，每一步都该有；警告是关于下一步的判断。合并两者会让一个仅仅“很大”的步骤读起来像危险步骤。
- **每轮只警告一次。** 否决：一轮可以长达上百步，而危险恰恰会在写完文件之后再次进入。

## 后果

- 带宽内的某一步可能同时收到两条消息：上一条工具结果带来的读数，以及针对本步的警告。它们独立调度、独立去抖，所以测试断言的是各自出现一次，而不是断言合并后的条数。
- 带宽需要已发布的上下文窗口。路由不发布窗口时警告静默，读数仍报告原始数字；对着未知分母给带宽定尺等于凭空编一个。
- 两次占用测量可能相差一个工具结果：读数在 post-execute 测量，警告在 pre-step 测量，若中间是没有任何工具调用的一步，警告看到的就是同一个数字。两次测量都走同一个 meter，因此它们对同一个请求绝不会给出不同答案，不同的只是请求本身。
- guard 现在监听两个接缝、为每个 agent 保存两个基线。两者都只对本插件自己的监听器可见，这也是 `invariant.ts` 仍然什么都不断言的原因：不存在一个由本包拥有、可供检查关系的持久事件。
- 警告没有经过标定。`observationMultiplier: 2` 与 `observationWindow: 3` 只是关于会话工具结果方差有多大的猜测；尺寸相差一个数量级的会话，带宽也会跟着差一个数量级。在真实录制上测量这一点属于未完成的延后工作，不是已有结论。
